# 网页端计算机组成原理教学智能体设计流程

## 一、项目定位

目标是设计一个网页端智能体，支持计算机组成原理课程中的：

- 章节知识问答
- 可视化推演
- 交互式仿真
- 汇编指令逐步解释
- 学习评价与反馈

整体思路是：**知识解释交给大模型，精确计算交给程序，动态展示交给前端，教学流程交给智能体调度。**

---

## 二、总体开发流程

建议将系统建设分为 8 个阶段，先完成最小可用版本，再逐步扩展复杂能力。

```text
第 1 步：明确智能体的核心场景
第 2 步：设计知识体系与内容库
第 3 步：确定系统总体架构
第 4 步：开发最小可用版本 MVP
第 5 步：加入可视化推演能力
第 6 步：开发交互式仿真模块
第 7 步：设计智能体工作流
第 8 步：开展教学评价与迭代
```

---

## 三、第 1 步：明确智能体的核心场景

首先需要明确系统到底解决哪些教学问题，而不是一开始就设计成万能系统。

当前需求可以拆解为 4 类核心能力：

| 能力 | 用户想完成什么 |
|---|---|
| 章节知识问答 | 学生询问课程概念、原理、公式、例题 |
| 可视化推演 | 将抽象过程转化为图形化、步骤化展示 |
| 交互式仿真 | 学生修改输入参数，观察系统状态变化 |
| 汇编指令逐步解释 | 输入汇编代码，逐条解释寄存器、内存、控制过程 |

### 建议第一版重点支持的章节

建议第一版优先聚焦高频、适合可视化和仿真的内容：

1. 数据表示：原码、反码、补码、浮点数  
2. 运算器：加减法、溢出、乘除法  
3. 指令系统：指令格式、寻址方式、汇编解释  
4. CPU：数据通路、控制信号、流水线  
5. 存储系统：Cache 映射、命中率、地址划分  

---

## 四、第 2 步：设计知识体系与内容库

智能体的回答质量不仅取决于大模型，也取决于知识库的组织方式。

建议将课程内容组织为三层。

### 1. 知识点层

以“补码”为例：

```text
补码
├── 为什么需要补码
├── 补码表示规则
├── 补码加法
├── 补码减法
├── 溢出判断
└── 典型例题
```

### 2. 教学解释层

每个知识点不只保存定义，还应包含：

```text
概念解释
直观类比
公式推导
典型例题
常见误区
可视化方案
课后小测
```

### 3. 结构化数据层

为了支持可视化推演和交互式仿真，需要将关键过程结构化。

例如补码加法：

```json
{
  "topic": "补码加法",
  "input": ["x = +5", "y = -3"],
  "binary_steps": [
    "x = 00000101",
    "y = 11111101",
    "sum = 00000010"
  ],
  "result": "+2",
  "overflow": false
}
```

普通 RAG 知识库主要支持问答，而可视化推演和交互式仿真需要额外的结构化过程数据。

---

## 五、第 3 步：确定系统总体架构

网页端智能体可以采用如下架构：

```text
前端页面
  ├── 聊天问答区
  ├── 可视化推演区
  ├── 仿真控制区
  └── 汇编代码输入区

后端服务
  ├── 智能体调度模块
  ├── 课程知识库检索模块
  ├── 推理与解释生成模块
  ├── 可视化数据生成模块
  ├── 仿真执行模块
  └── 汇编解释模块

数据层
  ├── 课程教材 / 讲义
  ├── 知识点结构库
  ├── 例题库
  ├── 指令语义库
  └── 仿真规则库
```

### 核心设计原则

不要让大模型承担所有工作。

建议采用：

```text
大模型：负责理解问题、组织语言、生成教学解释
规则程序：负责补码计算、Cache 地址划分、流水线推进等确定性推演
前端组件：负责动画、表格、流程图、状态变化展示
智能体调度器：负责判断用户意图并调用不同模块
```

## 六、第 4 步：开发最小可用版本 MVP

第一版不建议同时实现所有能力，而应先做一个稳定可用的最小版本。

### MVP 功能一：章节知识问答

支持学生提问，例如：

```text
为什么补码可以把减法变成加法？
Cache 直接映射和组相联映射有什么区别？
指令周期和机器周期有什么关系？
```

实现流程：

```text
课程资料
  ↓
文本切分
  ↓
向量化
  ↓
知识检索
  ↓
大模型生成回答
```

### MVP 功能二：基础汇编指令逐步解释

先支持少量基础指令，例如：

```asm
MOV R1, #5
MOV R2, #3
ADD R3, R1, R2
```

输出示例：

```text
第 1 步：MOV R1, #5
含义：将立即数 5 写入寄存器 R1
执行后：R1 = 5

第 2 步：MOV R2, #3
含义：将立即数 3 写入寄存器 R2
执行后：R2 = 3

第 3 步：ADD R3, R1, R2
含义：R3 = R1 + R2
执行后：R3 = 8
```

### MVP 功能三：补码推演

输入：

```text
x = +5
y = -3
位数 = 8 位
```

输出：

```text
+5 的补码：00000101
-3 的补码：11111101
相加结果：00000010
最终结果：+2
是否溢出：否
```

---

## 七、第 5 步：加入可视化推演能力

可视化推演是网页端智能体区别于普通聊天机器人的关键优势。

### 优先支持的可视化内容

| 知识点 | 可视化形式 |
|---|---|
| 补码加法 | 二进制位逐位相加、进位变化 |
| 溢出判断 | 符号位、进位、结果范围高亮 |
| 浮点数表示 | 符号位、阶码、尾数拆分 |
| Cache 映射 | 主存块映射到 Cache 行 |
| 指令流水线 | IF、ID、EX、MEM、WB 时间表 |
| 数据通路 | 指令执行时各部件连线高亮 |

### 可视化数据设计示例

以流水线为例，后端可以返回：

```json
{
  "type": "pipeline",
  "instructions": ["I1", "I2", "I3"],
  "stages": ["IF", "ID", "EX", "MEM", "WB"],
  "timeline": [
    ["IF", "ID", "EX", "MEM", "WB"],
    ["", "IF", "ID", "EX", "MEM"],
    ["", "", "IF", "ID", "EX"]
  ]
}
```

前端根据该 JSON 数据渲染为表格、动画或流程图。

## 八、第 6 步：开发交互式仿真模块

仿真模块建议独立开发，尽量不要完全依赖大模型。

可以按章节拆成多个小仿真器。

### 1. 数据表示仿真器

输入：

```text
十进制数：-13
位数：8 位
表示方式：补码
```

输出：

```text
原码：10001101
反码：11110010
补码：11110011
```

### 2. 缓存仿真器

输入：

```text
主存地址：0x3A7
Cache 行数：16
块大小：4B
映射方式：直接映射
```

输出：

```text
块内地址：2 bit
Cache 行号：4 bit
Tag：剩余高位
是否命中：根据当前 Cache 状态判断
```

### 3. 流水线仿真器

输入：

```asm
ADD R1, R2, R3
SUB R4, R1, R5
```

输出：

```text
存在 RAW 数据冒险
SUB 指令需要等待 ADD 写回 R1
可通过暂停或转发解决
```

### 4. 汇编执行仿真器

需要维护以下状态：

```text
寄存器状态
内存状态
程序计数器 PC
当前指令
执行阶段
标志位状态
```

建议从简化 ISA 开始，不要一开始就支持完整 x86 或 ARM 指令集。

## 九、第 7 步：设计智能体工作流

智能体不应该只是一个“大模型回答器”，而应包含任务识别和工具调度能力。

### 总体工作流

```text
用户输入
  ↓
意图识别
  ↓
判断任务类型
  ├── 知识问答 → 检索课程知识库 → 生成解释
  ├── 例题讲解 → 调用推演模块 → 生成步骤
  ├── 可视化请求 → 生成结构化可视化数据
  ├── 仿真请求 → 调用仿真器 → 返回状态变化
  └── 汇编解释 → 调用指令解析器 → 逐步解释
```

### 示例一：汇编解释任务

用户输入：

```text
帮我解释一下这段汇编每一步做了什么
```

执行流程：

```text
识别为汇编解释任务
  ↓
调用汇编解析器
  ↓
模拟寄存器变化
  ↓
生成逐步解释
  ↓
前端展示代码高亮 + 状态表
```

### 示例二：知识问答任务

用户输入：

```text
为什么补码减法可以转成加法？
```

执行流程：

```text
识别为知识问答任务
  ↓
检索补码相关知识
  ↓
生成概念解释
  ↓
给出二进制例子
  ↓
可选生成可视化推演
```

## 十、第 8 步：开展教学评价与迭代

系统上线后需要持续评估，而不是只看能不能回答问题。

### 评价指标

| 指标 | 评估问题 |
|---|---|
| 正确性 | 计算结果、概念解释是否正确 |
| 可解释性 | 学生是否能看懂每一步 |
| 交互性 | 学生能否修改输入并观察变化 |
| 鲁棒性 | 输入错误代码时能否提示原因 |
| 教学适配性 | 是否符合课程章节和教学目标 |
| 可视化质量 | 图示是否真正帮助理解 |
| 可扩展性 | 是否方便增加新章节、新仿真器 |

### 测试集设计

建议准备一套教学测试集：

```text
100 个章节知识问答
50 个补码 / 浮点数推演题
50 个 Cache 地址划分题
50 个流水线冒险分析题
50 段汇编指令解释题
若干错误输入与边界案例
```

每次系统更新后都运行测试集，检查是否出现能力退化。

## 十一、推荐开发路线

建议按如下顺序推进：

```text
第 1 阶段：章节知识问答
第 2 阶段：补码 / 浮点数 / Cache 的规则推演
第 3 阶段：汇编指令逐步解释
第 4 阶段：前端可视化展示
第 5 阶段：交互式仿真
第 6 阶段：流水线、数据通路等复杂动态仿真
第 7 阶段：教师端管理与题库评测
```

最合理的 MVP 是：

```text
知识问答 + 补码推演 + 简单汇编逐步解释
```

## 十二、技术选型建议

| 模块 | 推荐技术 |
|---|---|
| 前端框架 | Vue / React |
| 可视化 | ECharts / D3.js / Mermaid / SVG |
| 后端框架 | FastAPI / Flask |
| 知识库格式 | Markdown + JSON |
| 向量数据库 | FAISS / Milvus / Chroma |
| 大模型 | API 模型或本地 Qwen / DeepSeek / Llama |
| 仿真器 | Python 规则引擎 |
| 汇编解析 | Python Parser / 简化 ISA 解释器 |
| 数据存储 | SQLite / PostgreSQL |
| 用户记录 | MySQL / PostgreSQL |
| 代码版本 | git |

## 十三、最终系统模块划分

最终可以将平台划分为 6 个子智能体：

```text
1. 课程问答智能体
2. 例题讲解智能体
3. 可视化推演智能体
4. 汇编解释智能体
5. 交互仿真智能体
6. 学习评价智能体
```

它们共享同一个课程知识库，但分别调用不同工具或模块。

---

## 十四、核心总结

整个系统建设可以概括为：

```text
从课程知识库开始，
以知识问答作为入口，
用规则模块保证推演正确，
用前端可视化增强理解，
用仿真器支持交互探索，
最终形成面向计算机组成原理的教学智能体平台。
```

最重要的设计原则是：

```text
大模型负责解释，
规则程序负责计算，
前端负责展示，
智能体负责调度。
```
